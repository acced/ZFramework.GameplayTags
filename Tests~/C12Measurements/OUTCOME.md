# C1 / C2：局部优化与完整观测结果

## 结论与限制（2026-10-15）

本次 PR 更新是可审查的局部改进，**没有通过“所有路径普遍更快”的性能验收，也不表示可以直接合并**。只修改空/单成员复制与包含扫描后的后缀合并；不引入 P1 表示、交集/差集新策略或新的阈值策略。

必须同时保留的代价与不确定性：

- C1 阶段的 1024 成员完整生命周期相对当前 PR 基线 B11 四对均较慢：1.00932 / 1.08387 / 1.09544 / 1.13410；配对比值中位数 1.0897，绝对中位数约 286.21 对 262.66 µs。分配相同。后续 C2 阶段得到不同的生命周期结果，不能替换或抵消此结果。
- C2 的新建/增长 append 工作流虽然少分配 8,176 B/次，相对 C1 仍有三对较慢，配对中位数约 1.0167。右别名的时间结果混合。
- C1 的 240 行中 51 行、C2 的 480 行中 293 行不足 250 ms。保留全部短批次、GC 和异常分配小数，不剔除离群值。
- 同一物理二进制 A/A 在补足只读控制时长后仍存在约 5–19% 的配对变动；跨构建未修改源码的控制也有变动。它们限制小幅收益的归因，不能作为减法校正或统计接受阈值。
- 仅在本地 Linux x64、.NET SDK 8.0.425 / CoreCLR 8.0.31、关闭分层编译的环境测量。没有 Unity 2021.3、Mono、IL2CPP 或设备端性能结论。

观察到的局部收益：

- C1 的空/单成员保留容器复制工作流，相对 B11 的配对时间中位数比值分别约 0.566、0.677、0.725、0.753；分配没有变化。此工作流包含恢复目标的 CopyFrom，不能解释成单独复制内核的时间。
- C2 的末尾缺失成员、保留容量 append / 左别名合并，相对 C1 四对均较快，配对中位数比值约 0.877 / 0.887。右别名约 0.948，但只有两对较快。
- C2 新建/增长 append 与右别名工作流的分配均为 24,672 → 16,496 B/次，最终容量 2,047 → 1,025。保留容量路径仍是 0 B/次；容量换算的数组负载不是整个堆的保留内存。
- 首个对象诊断存在小数分配观测。例如 append 的旧路径约 16,400–16,401.396 B/次，新路径约 8,224–8,225.450 B/次。完整原始值保留，未修整成理论数组大小，也未推断其原因。

## 测量与修复历史

每个格子、版本、配对轮次使用独立进程。四轮固定平衡相对顺序；每格仅由 B1 选取共享调用次数。包含完整公开工作流与分开的首对象/孤立/冷进程诊断。所有数值先写出，再验证内容、顺序、代表对象、来源和尾槽；没有候选方自适应次数、控制减法或择优复测。

1. 原始 90 次 B1 校准与 64 次同物理 B11 二进制 A/A 全部保留。错误地把修改 List 的版本计数上限用于四个只读控制，导致其基线不足 250 ms；原始 A/A 有 47/64 行短批次。
2. 独立修复仅四个只读控制调用次数，由已保存 B1 时间推算固定约 300 ms；执行四次固定 B1 检查与 32 次受影响 A/A，不重新测量原来的 32 个修改路径哨兵。检查与 A/A 全部超过 250 ms，但变动仍存在。不宣称“消除了噪声”。
3. C1 收集 240 行，C2 收集 480 行，全部验证通过。总共保存 910 条数值记录（含校准和控制修复）。没有后续源代码变体或额外计时。
