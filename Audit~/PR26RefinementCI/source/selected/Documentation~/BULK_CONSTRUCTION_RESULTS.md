已完成严格有序构造、覆盖式重建和一般乱序构造的实现、x64/ARM64 正确性与完整成本测量、下载后独立复核。保留有序直接物化作为准备阶段候选，特别是 Array 的非空输入和 Micro 的已测多成员输入；不把统一排序的 FromUnordered 当作所有表示的默认构造器。它对 Dense 有明显回退，空输入及 Micro 单成员也未获得一致收益。

## 实际减少了哪些工作

FromSortedUnique 先检查全部输入的注册表所有者和严格递增性，然后使用私有分配入口直接建立结果。Array 顺序提取句柄中的 ID；Dense 按机器字累积位再写入；Micro 按局部区间合并成员位。已经验证的唯一输入长度就是准确 Count，不再逐项维护计数或完成后扫描人口计数。

ResetFromSortedUnique 在全部输入校验通过后才允许扩容、清空和写入。最后一个标签无效不能导致旧结果半清空。已有容量足够时为零分配；不改变表示，也不依赖全局临时缓冲。

FromUnordered 另建临时 int[]，解析、排序、去重后物化；这些成本均在计时内。所有构造保留与预先预约容量的旧循环相同的容量公式，不以容量缩水制造收益。无新增实例字段、缓存、对象池、COW、借用输入或延迟 Count。

旧 AddTag 对默认句柄返回 false 的合同不变。新的严格 Builder 拒绝默认和外域句柄，属于明确的新 API 合同。性能对照仅比较两者共同接受的有效输入；不能称它们在所有无效输入下完全等价。调用期间禁止并发修改输入。

## 测量环境和合同

两平台均为 Ubuntu24.04.5、实际 SDK8.0.425、目标 net8.0、运行时 .NET8.0.31、Release。global.json 指定 SDK 且 rollForward=disable，CLI 实测版本也检查通过。关闭分层编译和 ReadyToRun，固定一个允许的 CPU。

三轮乱序进程执行，每轮七个完整样本。每场景校准目标约1ms，同时保留16MiB 每样本分配上限及迭代上限。所有原始耗时、实际分配、GC代际增量与样本时长均保留。循环控制和候选位于同一真实调用方，整次操作之外才分派；A/A 使用相同二进制、相同路径，以两个标签重复执行。

输入为预解析 RuntimeTag 句柄。注册表构建与名称解析在两侧均不计入操作；有序候选的所有者检查、有序/唯一校验、分配、填充和准确计数全部计时。乱序候选的工作区、排序、去重也全部计时。

注册表规模为10,000/65,536/262,144个显式定义，采用平坦 B.T... 名称，另外包含一个 B 祖先。因此最大实际编号域262,145，Dense需要4,097个ulong；不能套用历史层级夹具中的266,241个编号。成员数0/1/8/32/128/1024/4096，三种局部性、两个种子。输入分别为严格有序、逆序、随机乱序与带重复乱序。排序构造、预分配覆盖、建立输入后1次或16次原Union分别报告。

两平台分别测量，不混用最快样本。相同5%每轮规则只是筛选，不是统计置信区间；下面按规模的归类是对固定数据的事后分析，不是已经实现或验证的新策略阈值。

## 三、生命周期不能由构造最快者直接决定

ARM64、262,144显式定义、4096连续成员，使用新的有序构造。单位微秒/整段工作，而非每次Union。

| 工作 | Array | Dense | Micro |
|---|---:|---:|---:|
| 只构造一次 |6.737|6.808|7.504|
| 构造后执行1次原Union |13.411|9.946|8.063|
| 构造后执行16次原Union |110.586|52.576|17.609|

这些是实际整段计时，不是把各段最好的数相加。三种构造都比自己的旧循环省工作，但后续重复运算仍让Micro在此集中成员负载中占优。换成4096分散成员，新构造+16次并集为Array205.444us、Dense53.765us、Micro204.695us，优选再次变化。

这支持下一阶段将输入有序性、N、全域W、Micro16占用数、运行关系和后续操作预算用于选择。它不等于已经写好了Auto，也不提供每行任意挑选最快表示的产品。

## 四、必须保留的失败结果

### 空输入与单成员

每个固定成员数有18个分布/注册表/种子场景。Array有序非空的108个场景中：x64新建107个、覆盖108个每轮至少快5%；ARM64均108个，未出现相对两个对照每轮慢超过5%的非空场景。但空输入的x64/ARM64新建分别15/18、17/18更慢；覆盖均18/18更慢。

Micro在已测成员数8/32/128/1024/4096形成的90个场景中，两CPU的新建和覆盖各90/90每轮至少快5%。这不是“任意N>=8都已验证”。ARM64单成员新建和两CPU单成员覆盖均18/18持续变慢。旧内联单成员路径不应被通用Builder无条件替换。

### 统一先排序不是Dense乱序构造的优化

4096个成员原本来自连续区间，但输入随机打乱；262144定义、种子20261002，单位us。

| CPU / 表示 | 原逐项Add | 先排序再批量 | 原/新分配B |
|---|---:|---:|---:|
| x64 Array |481.448|130.416|16456 / 32864|
| ARM64 Array |475.051|112.961|16456 / 32864|
| x64 Dense |16.802|130.476|32848 / 49256|
| ARM64 Dense |13.483|119.262|32848 / 49256|

排序可以避免Array的大量反复查找和搬移，却给本来就可直接置位的Dense增加了不必要工作。一般乱序Dense候选不作为默认路径采用；原代码及所有慢样本仍在证据中。不能用有序版本分数代替这个入口，也不能将临时int[]排除于分配统计。
