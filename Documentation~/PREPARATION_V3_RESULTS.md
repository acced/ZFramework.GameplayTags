# Preparation v3：重组后的真实版本与生命周期验证

日期：2026-10-02。PR：https://github.com/acced/ZFramework.GameplayTags/pull/14

## 结论

这轮完成的是一个真实重新编译的候选：保留 PR13 新建路径，恢复 PR12 完整 Reset 调用链，在参数验证和独立目标分配后跳过空源转换扫描。

2、8 成员 Reset 回退恢复到 PR12 附近；两个平台的三个表示各 72 个 Reset 测点，相对 PR12 均没有触发三轮持续超过 5% 的退化筛选。相对 PR13 的空/单成员收益会丢失，不能隐瞒。

空 Dense 转 Array/Micro 不再扫描全域，获得大幅减少工作量的实测收益；但同一个分支加入后，x64 非空 Dense→Micro 的两个分散场景出现持续回退。因此仍不批准整包替换生产。

最重要的新发现：当对端表示不变时，只转换一侧常常让混合集合运算抵消转换收益。原先同表示内核的最快成绩不能直接用于每个对象独立选择表示的规则。没有实现或验收自动选择器。

## 2. 保留新建方法，不代表每个读数自动稳定

每个平台每个表示288个fresh测点（含四种输入次序），相对v2没有触发持续5%退化筛选。但具体中位数仍有回退和显著波动；不能写成全部不退。

例：同轮ARM64 4096连续Micro sorted新建，v2为5.993us，v3为7.580us；同轮x64 4096连续Array为v1 6.281us、v2 10.290us、v3 10.190us。它们虽然未通过三轮持续退化筛选，原始坏样本仍在，也不能作为已经稳定获益的依据。

相对v1，ARM64 10000定义/4096分散Micro sorted新建在两个种子上持续退化：7.008→9.032us、7.038→8.924us，两个A/A通过。x64还有一个Micro乱序重复fresh退化。

八个分散Array的新建仍接近v2：x64 34.949→34.423ns，ARM64 26.997→26.944ns，均104B。不把源码没改的微小差别算作新增算法收益。

## 4. 保持、转换、直接构造：这次对端不免费变换

两个起点分开计量。

- input从已解析、有序、唯一的句柄开始。keep构造原表示；convert构造原表示再转换；direct直接构造目标。
- live从现有集合开始。keep不克隆；convert独立转换；direct在计时内导出RuntimeTag[]并枚举，再构造目标。其导出与验证并非免费。
- 每组所有策略使用同一个对端对象，它保持原始源表示。因此一侧转换后会实际运行混合表示操作。
- uses=0/1/16，每次是独立Union(prepared,peer)，不是不断增长结果的累积链。
- live/keep/0保留源对象身份，不是独立复制，也不参与原四项新建合同排名。

### 源码中已确认的混合路径成本

Runtime的DenseFusion仅在相关输入和输出都是Dense时启用。混合结果仍走通用复制、追加或枚举。

Micro混合Union使用两个Records枚举器再逐记录PutRecord；Records遇到Dense时按每16个编号的小区间遍历全域，而不是先跳过非零机器字。因此“只有8个成员”也可能扫描大量空区间。源码位置：固定测量提交的 `Audit~/MicroBitmapSet.cs` 中UnionCore和Records.MoveNext。

这些是源码确认的执行工作，但没有声称仅一项就解释全部CPU差距。下一项应优先比较混合表示专用结果内核及付费的对端协同准备，而不是用同表示最快成绩拟合单集合选择器。

## 5. 真实调用点与辅助诊断

主ConstructionLoop反汇编中，x64 v2明确调用ResetFromSortedUnique，v1/v3对应路径被内联。ARM64也保留了v2独立方法与v1/v3调用方生成代码。

为排除只有大夹具出现该趋势，另编译未改的v1/v2/v3，使用只有Reset的真实调用点。辅助夹具首次错误调用Set.Select，因Set仅提供foreach模式而非IEnumerable而编译失败；改为untimed foreach校验后，两平台成功执行run36971172133。没有修改库API或主计时源码来修补夹具。

ARM64独立调用点中v3/v1两家族各24个场景没有持续5%退化且A/A均通过。v2在独立调用点也保留调用，不是只在大ConstructionLoop中发生。不能由此认定某个具体JIT预算是全部差异的原因，诊断绝不替换主矩阵。

## 6. 正确性、分配与复核

- 转换/所有权附加测试2,812,172断言；

每CPU独立复算23,328汇总行、69,984原始行、489,888耗时样本；86,688个零分配样本包含Reset、预分配CopyFrom和明确不创建对象的live/keep/0，不能全归为新增API成绩。64个生产保护文件（含package）未改。

collect重新下载两平台原始产物，核对SHA、精确Git树、同二进制A/A、源文件跨CPU一致性，再重算完整数据。合计46,656汇总行、14,544比较行、13,824生命周期汇总行。全部慢样本和GC回收计数保留。

## 限制与下一项工作

SDK8.0.425明确锁定、.NET8.0.31、Ubuntu24.04.5、Release、CPUaffinity、Tiered/ReadyToRunoff。0.5ms校准受8MiB分配上限约束，7样本×3独立轮次。与旧校准或其他机器绝对ns不混用。

持续5%只作筛选而非置信区间；特别是Dense新建、转换的A/A仍有波动。源码不变也不能自动删除坏样本。并未完成真实Unity/Mono/IL2CPP/Burst/移动设备、冷缓存多角色、持续变更轨迹或长期峰值内存验收。

后续方向：保留可解释的直接构造，先改善混合表示Union/Append/Remove的结果构造和非零字枚举；再测量对端也参与准备时的总成本，最后制定并在留出输入上验证选择规则。当前没有Run容器、统一三表示类型、自动转换、发布或原四项全面领先结论。
