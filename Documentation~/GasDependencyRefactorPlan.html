划清「纯 C# 本体」与「引擎能力部分」

其他现状

  • ZFramework.GameplayTags.asmdef：noEngineReferences: false，一个程序集同时装着纯逻辑和 MonoBehaviour。
  • 生成代码（Assets/GameplayTags.Generated，程序集 ZFramework.GameplayTags.Generated）在 #if UNITY_5_3_OR_NEWER 下使用 [Preserve] 和 [RuntimeInitializeOnLoadMethod]。它是只被项目代码引用的叶子程序集，GAS 本体不引用它，可以保留引擎引用。
  • YeeYo.Gas.asmdef：同样是 noEngineReferences: false。README 里说的「仅 mscorlib + System」目前只靠自觉，编译器并不检查。

04关键决策：Unity 序列化回调放哪里

Core 不能实现 UnityEngine.ISerializationCallbackReceiver，而 C# 的 partial 类型不能跨程序集，所以 Unity 层也没法给 Core 类型补上这个接口。一共三条路：

方案 A · Core 只负责名称，Unity 层提供序列化代理 推荐

  • GameplayTag：保留 [Serializable]、[DataContract] 和公共字段 m_Name，Unity 依旧能序列化名称，现有 Drawer 依旧可用。去掉回调后，Unity 加载出来的 handle 需要调用方在加载边界自己 Resolve()。源码注释里本来就是这个契约（“Unity owners must assign Resolve() for standalone struct fields after loading”），所以没有引入新契约。
  • GameplayTagContainer：去掉 [Serializable]，免得 Unity 序列化出一个「有名称、没存储」的半成品，导致查询静默返回 false。保留 [DataContract] 路径。把现有的 OnBeforeSerialize/OnAfterDeserialize 改名为公开方法 CopyExplicitTagNamesTo(List<string>) / SetExplicitTagsFromNames(IReadOnlyList<string>)。
  • Unity 层新增 GameplayTagContainerField。它的内部字段和原来同名（m_SerializedExplicitTags），所以把 MonoBehaviour 里的字段类型从 GameplayTagContainer 换成 GameplayTagContainerField 时，YAML 数据可以原样读回。

代价：Inspector 里的容器字段类型要改名。好处：Core 查询热路径一个分支都不加，依赖方向干净，也和 GAS 的「资产在 Unity 层 → 定义在本体」模式一致。

方案 B · Core 内惰性恢复

Core 容器在每次查询时检查「有序列化名称但存储未建」，必要时就地重建。这样兼容性最好，但 HasTag 等热路径要多一个分支和一个字段读取，违背这个包「caller-contract performance core」的定位。另外反序列化后「谁、在哪个线程」触发重建也变得不确定。不推荐。

方案 C · Core 引用 UnityEngine.CoreModule

直接违反「仅 mscorlib + System」的约束，GAS 本体也就无法在纯 .NET 环境下单测。否决。

方案 A 草图

// Runtime/Unity/GameplayTagContainerField.cs — ZFramework.GameplayTags.Unity
namespace GameplayTags
{
    /// Unity 序列化代理：持久化显式标签名，运行时 handle 只在 Core 容器里。
    [Serializable]
    public sealed class GameplayTagContainerField : UnityEngine.ISerializationCallbackReceiver
    {
        // 与旧 GameplayTagContainer 同名，字段类型替换后 YAML 原样读回。
        [UnityEngine.SerializeField] private List<string> m_SerializedExplicitTags = new();
        [NonSerialized] private readonly GameplayTagContainer m_Value = new();

        public GameplayTagContainer Value => m_Value;

        public void OnBeforeSerialize() => m_Value.CopyExplicitTagNamesTo(m_SerializedExplicitTags);
        public void OnAfterDeserialize() => m_Value.SetExplicitTagsFromNames(m_SerializedExplicitTags);

        public static implicit operator GameplayTagContainer(GameplayTagContainerField field) => field.Value;
    }
}

Editor：GameplayTagContainerPropertyDrawer 的 [CustomPropertyDrawer] 目标改成 GameplayTagContainerField。它按 "m_SerializedExplicitTags" 查找属性，内部逻辑不用改。GameplayTagPropertyDrawer 仍然针对 Core 的 GameplayTag，Editor 程序集本来就引用 Core。

06行为差异与处理

差异点旧（GAS 自带）新（ZFramework）处理
添加/移除事件 OnTagAdded / OnTagRemoved 只针对显式标签 OnAnyTagNewOrRemove(tag, newCount) 对隐式祖先也触发：加 A.B.C 会依次通知 A、A.B、A.B.C 本体内部没有订阅者（已用 grep 确认）。README 改为推荐 RegisterTagEventCallback(tag, NewOrRemoved, cb) 按标签订阅。外部订阅方属于破坏性变更。
None / 未注册标签 AddTag(None) 被静默忽略 契约要求 handle 已注册且非 None。AddTag(None) 会把 id 0 写进存储，之后 HasTag(None) 返回 true 在边界上校验：GameplayTagSet 构造时对 !IsValid 抛 ArgumentException；ASC 公开的增删入口加 Debug 断言。
字符串隐式转换 零分配，任意字符串都能用 RequestTag 走字典查找；首次调用会触发注册表初始化；未知名称返回 None README 里删掉「零分配」的说法。热路径用生成的 Tags.* 字段或缓存的 handle；字符串只用于冷路径和配置。
RemoveTag 返回值boolvoid；移除次数超过显式计数属于契约违例 GAS 内部增删本来就对称（效果授予/移除、能力激活/结束），影响不大。外部调用方的签名会变。
回调中抛异常后续标签的结构清理可能被打断 状态先提交、再派发；抛异常时丢弃剩余排队事件 GameplayEffectContainer 第 589 行「逐项移除」的写法继续保留：结构总是一致，但后面的通知可能丢失，这一点写进文档。
Clear()先清空，再只通知显式标签，处理了重入 对所有条目（含祖先）派发 newCount = 0，重入的变更追加到同一个队列 重入语义等价。用阶段 0 的特征测试覆盖。
注册表生命周期无注册表每个进程/域只初始化一次，之后冻结 单测：在 assembly 级 SetUp 里一次性 GameplayTagManager.Initialize(...) 注册所有测试用标签，各测试类不能自己初始化。

  • 两个 Core asmdef 的 noEngineReferences: true 就是编译期护栏：以后谁在本体里写 using UnityEngine 都会直接编译失败。
  • 可选：CI 里跑两个纯 .NET csproj 的 build，防止有人通过 #if UNITY_* 绕过护栏。

09风险与待决问题

#事项建议
R1包内 bin/、obj/ 会被 Unity 导入：GameplayTags.Runtime.dll 和 asmdef 编出的程序集定义了同样的类型，可能出现重复类型或引用歧义。 阶段 1 删除，并把 csproj 输出改到 .build~/。加 .gitignore。
R2现有 ZFramework 用户在 MonoBehaviour 里声明了 GameplayTagContainer 字段：去掉 [Serializable] 后，Unity 不再序列化该字段。如果在改成 Field 类型之前重新保存了场景，数据会丢失。 迁移说明写明：升级包和修改字段类型放在同一次提交里，期间不要保存资产。或者在 3.0 里保留一个 [Obsolete] 过渡期。
R3Unity 加载出来的 GameplayTag 字段不再自动 Resolve（以前依赖 #if UNITY 回调）。 契约本来就要求调用方在加载边界 Resolve。GAS 的资产全部经 Definition 构建，正好就是这个边界。待决：要不要在 Unity 层也提供一个 GameplayTagField，做到和容器对称？
R4事件会对隐式祖先触发，外部订阅 OwnedTags 事件的代码行为会变。 GAS 是 0.1.0，破坏性变更可以接受；README 给出 RegisterTagEventCallback 的写法。
R5注册表冻结后就不能重新初始化：Editor 不进行 Domain Reload 时，新增标签必须重新生成代码并编译。 这是 ZFramework 现有的行为，不在本次范围内，只在 GAS README 里提一句。
Q1OwnedTags 是直接暴露 GameplayTagCountContainer，还是只暴露只读接口加 ASC 上的 AddLooseTag / RemoveLooseTag？ 倾向后者：外部直接 RemoveTag 能把效果授予的计数减掉，破坏不变量。但这超出「依赖划分」的范围，可以单独立项。
Q2阶段 3 的资产迁移：有没有已经存在、需要保留的 .asset 数据？ 没有的话直接换字段类型，省掉迁移代码。
