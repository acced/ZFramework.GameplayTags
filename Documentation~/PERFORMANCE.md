# 2.0 性能实现与测量记录

这一版优先优化缓存标签句柄后的查询、反复增删、计数和遍历。原实现中的排序列表、删除时重建整个祖先集合、三个计数字典和每个标签各自持有的后代数组，已替换为共享的整数注册表、紧凑存储与开放寻址索引。

在本次 .NET 8 x64 场景中，1,024 个显式标签的精确命中查询从 **23.119 ns/次降至 3.006 ns/次**；成功删除再恢复同一标签，从 **9,956.449 ns/对降至 47.090 ns/对**。这是同一工作负载对固定旧提交的测量，不是其他库之间的排名，也不能直接代表 Unity / IL2CPP。

交换条件是更大的容量与索引开销：该场景普通容器的近似常驻托管内存从 **12,440 B 增至 53,400 B**。4 和 16 个显式标签的全新容器构建中位时间也更慢。完整收益和退步均保留在下面及原始数据中。

## 数据结构为什么这样选

### 注册表：冻结的 DFS 区间和共享路径

注册期间自动补全父标签，按区分大小写的 ordinal 兄弟顺序进行真正的深度优先前序编号。每个标签拥有整数 ID、父 ID 和子树末端。严格祖先关系等价于判断后代 ID 是否落在父节点之后、子树末端之前，因此 `IsParentOf` / `IsChildOf` 不再扫描标签数组。

后代访问直接引用全局前序数组的连续切片。祖先路径使用共享的根到叶路径池，同一路径上的节点引用前缀。深度 3,000 的单链只需要 3,000 个路径槽位；分支树的路径池成本仍与所有叶路径的深度之和有关，不能声称任意树形都只有 O(N) 路径存储。

名称到 ID 的 Dictionary 留在初始化和名称解析边界。显式 `Initialize(...)` 可以跳过程序集反射扫描。性能敏感代码应先解析并缓存句柄，再进行整数操作。

### 每个容器：连续条目、显式索引与平坦哈希

`TagStorage` 的一个条目包含四个 int：标签 ID、总贡献次数、显式次数、显式索引位置，条目大小为 16 字节。另一个连续 int 数组只索引显式标签，让一个叶节点拥有很深祖先链时，显式枚举仍只访问一个条目。

初始不超过 8 个**包含祖先的不同标签**时使用线性扫描，避免小集合的哈希数组分配。超过阈值时建立 2 的幂大小的桶数组，负载不超过 0.5。桶存储条目下标加一，线性探测处理冲突；删除使用后移修复探测链，不积累 tombstone。条目删除采用末项交换，同时修复桶下标与显式索引。

这比为每个实体分配覆盖整个全局注册表的 sparse 数组更适合“大注册表、稀疏持有”的用法。不过它也明显比旧版两个紧凑 int 列表占用更多内存。容量按几何级数增长，并在 Clear 后保留以便复用；内存随保留容量而非仅随当前元素数量变化。

只计三种存储数组的数据区时，容量成本为 `16 × entryCapacity + 4 × bucketCapacity + 4 × explicitIndexCapacity` 字节，此外还要加上托管对象和数组头、容器及序列化字段的成本。`EnsureCapacity` 参数是包含祖先的总不同标签容量；预留得过大会直接增加内存。

### 增量维护祖先贡献

普通集合的显式标签只贡献一次。计数容器的显式标签按 amount 贡献多次。加入或删除只更新当前标签及其祖先路径上的计数；某祖先的贡献归零才从存储中移除。共享祖先不再触发全容器闭包重建。

没有事件监听器时直接完成计数更新。存在监听器时，操作先提交数据，再通过可复用通知队列派发；批量和内置父链操作先完成整批修改。回调重入与异常清理的正确性经过独立测试，但回调耗时不在本次计数基准中。

### 复杂度与前提

令 E 为显式不同标签数、T 为包含祖先的不同标签数、h 为当前标签的层级深度、Q 为查询集合的显式不同标签数。下面是单容器、无监听器、不含扩容的基础成本。哈希复杂度是正常分布下的期望复杂度，扩容还需要复制条目并重建索引。

| 操作 | 重写后的成本 |
| --- | --- |
| 严格祖先 / 后代关系 | O(1)，整数区间判断 |
| HasTag / HasTagExact / 读取计数 | 期望 O(1)；微小存储最多扫描 8 项 |
| 单标签增删、单标签 amount 变更 | 期望 O(h)，不随全部显式标签重建闭包 |
| 遍历显式标签 / 全部标签 | O(E) / O(T) |
| HasAny / HasAnyExact | 期望 O(min(T, Q)) / O(min(E, Q))，遇命中即返回 |
| HasAll / HasAllExact | 期望 O(Q)，遇不满足即返回；单条件有直接路径 |
| 普通容器 Copy 覆盖目标 | 期望 O(T目标 + T来源)，清理目标后复制数据并重建索引；自复制为 O(1) |
| 普通容器 Clone | 期望 O(T来源) |
| 计数容器复制到普通集合 | 按存在性重新计算闭包，期望 O(T目标 + 来源 E × h) |
| 子标签提取 | 扫描子树 ID 范围与相关持有数量中的较小一方 |

内置容器传播链上共有 P 个容器时，单标签更新基础成本为期望 O(P × h)。逐标签监听使用排序回调数组的二分查找，派发还需支付实际通知成本。amount 通过整数加减应用于内置容器；自定义接口父容器的兼容路径可能按次数逐次调用 AddTag / RemoveTag。

Set algebra、首次增长、事件订阅和序列化并不承诺零分配。具体类型的 foreach 使用结构体枚举器；接口枚举仍可能装箱。`GameplayTag` 为兼容 Unity 名称字段仍包含字符串引用，并非 4 字节结构体；容器存储使用的是 32 位 ID。

## 最终测量

环境为 Ubuntu 24.04.3 LTS、.NET 8.0.31、.NET SDK 8.0.425、X64、AMD EPYC 9V74 的 KVM 虚拟机。优化编译，JIT 分层编译与 server GC 均关闭。未绑定 CPU，未控制频率，其他共享宿主活动不可控。

每项完整测量保留 7 个样本，表中使用中位值。基准与重写进程顺序运行，计时期间没有本任务的构建和测试并行执行。结果包含循环与可观察结果消费的正常开销；纳秒级数值不是单条指令的延迟。

### 1,024 个显式标签，深度 3

“提速”为旧版耗时除以重写版耗时。增删按完整的一对操作报告，枚举按完整遍历报告。

| 操作 | 旧版 | 重写版 | 提速 |
| --- | ---: | ---: | ---: |
| 精确命中查询 | 23.119 ns/次 | 3.006 ns/次 | 7.69× |
| 精确未命中查询 | 21.070 ns/次 | 2.086 ns/次 | 10.10× |
| 精确混合命中 / 未命中查询 | 22.109 ns/次 | 2.650 ns/次 | 8.34× |
| 隐式父标签命中查询 | 22.792 ns/次 | 2.013 ns/次 | 11.32× |
| 成功删除后重新添加 | 9,956.449 ns/对 | 47.090 ns/对 | 211.44× |

| 已有显式计数加一再减一 | 163.474 ns/对 | 35.094 ns/对 | 4.66× |
| 遍历所有显式标签 | 5,789.786 ns/遍历 | 1,291.994 ns/遍历 | 4.48× |

## 对照的边界

工作负载包含 4,096 个深度 3 的叶标签，分布在 32 个父分组下。预先计算固定种子的 4,096 项句柄序列，命中与未命中使用分离的叶和父分组。名称查找、反射注册、随机数和查询数组构造不在计时内。

`IsParentOf/hit` 使用的根固定拥有 4,128 个后代，包括 4,096 个叶与 32 个分组，**并不随表中的容器显式数量缩小**。该行从数组扫描变成整数区间判断，原始表出现很大倍数；它不是所有树形或随机关系查询的普遍倍数。父成员命中最多访问 16 个不同父分组，缓存局部性也是本场景的一部分。

每组修改前后执行闭包、成员和计数语义检查，测量结果参与不会相互抵消的可观察 checksum；两份完整报告均得到 `-1524431612`。比较脚本还要求操作集合、单位、迭代数、运行时、系统、架构、GC、分层编译、注册表规模、查询序列长度和计时器频率一致。

旧版一般 HasAny / HasAll、交集与事件存在语义缺陷，这些路径没有用于提速声明。仅对已验证正确的单条件 HasAllExact 旧路径做对照。订阅回调、大批量父链、冷启动注册时间、序列化和其他第三方容器没有纳入这一轮性能数字。

本轮执行平台只有 .NET 8 x64。Unity 条件代码通过编译桩检查，源码生成器通过固定 Roslyn 3.8 / .NET Standard 2.0 验证；没有实际运行 Unity Editor、Mono、IL2CPP、AOT、ARM 或移动端基准。

## 检查、异常与正确性

热路径删除一般参数检查、警告日志、重复名称验证和异常包装，信任调用者提供有效标签、正的 amount、足够的可删除次数、无环父关系和正确的池所有权。重复添加与缺失删除的分支是集合语义的一部分，保留。枚举没有修改版本检测，容器没有并发写保护。

两处显式冷路径异常仍然存在：禁止替换已冻结注册表，以及调用者主动使用的 ValidateName。回调派发保留 finally 释放队列引用与恢复状态；CLR 数组边界检查由运行时管理。没有凭行数宣称“取消 99%”：优化对象是高频路径的工作量与实测成本。

最终主测试通过 **7,595,855 次断言，0 个失败组**，使用独立名称前缀、HashSet 和 Dictionary 模型验证确定性回归与随机操作。另有随机注册森林、3,000 层单链、源码生成器与 .NET DataContractSerializer 的实际往返验证。详细范围见 [测试说明](../Tests~/README.md)。

## 原始算法资料

- [LLVM Programmer's Manual：集合容器](https://llvm.org/docs/ProgrammersManual.html#set-like-containers-std-set-smallset-setvector-etc)：小集合线性扫描、DenseSet 的平坦存储与 SparseSet 的容量取舍。
- [EnTT 作者对 sparse set 的说明](https://skypjack.github.io/2020-08-02-ecs-baf-part-9/)：连续数据与末项交换删除的设计。这里采用相近的紧凑存储思想，成员索引使用哈希，不是照搬全注册表 sparse 数组。
- [Jeff Erickson：Depth-First Search](https://courses.grainger.illinois.edu/cs374al1/fa2025/notes/06-dfs.pdf)：DFS 子树连续区间及祖先关系。
- [Abseil Swiss Tables](https://abseil.io/about/design/swisstables)：控制字节、分组探测和 SIMD 优化。本实现使用标量线性探测，不等同于完整 SwissTable。

这些资料支持结构选型；本次实际数字来自仓库中的可复现基准。没有统一跨语言、硬件、标签密度、查询分布与修改比例的“世界最快”结论。
